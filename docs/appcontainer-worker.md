# AppContainer investigation — 31 October 2026

Decision from the repository owner: disable execution now and investigate a Windows AppContainer worker. No AppContainer profile, ACL, firewall rule, registry setting, or worker was installed during remediation. The native commands and runner reject all compilation/execution requests. There is no unsafe override.

The smallest credible Windows-native candidate is a separate, noninteractive worker using an AppContainer identity (consider LPAC where compatible), with no network capabilities. This keeps Tauri/React, local problem files, and SQLite in the trusted desktop process. It does not require a web service or container platform. This is a proposed design, not a verified isolation claim.

Microsoft's [AppContainer launch guide](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer) describes the package/capability SID access check and the stricter LPAC model. Ordinary AppContainers retain access to some resources granted to all application packages. Thus “AppContainer” alone must not be represented as an exclusive filesystem namespace. Compatibility and access to broadly readable host objects require an explicit review.

The worker must satisfy these conditions before execution can be enabled:

1. Use a fresh job identity and workspace. Grant that SID only the runtime/toolchain resources it needs, source/artifacts, and a bounded scratch volume. Grant no profile, app-data, database, statement/test suite directory, or other job directory access. Feed one case through an inherited pipe and use a fresh runtime workspace for each case. The AppContainer profile's own writable storage also needs containment and a hard quota; checking directory size after a job is insufficient. A bounded disposable VHDX is an option to investigate, with installation/privilege costs to evaluate. AppContainer alone does not enforce a disk quota.
2. Launch **both** g++ and Python syntax checking under the same file/network policy as solutions. g++ needs a small, bounded compiler process tree (cc1plus/as/ld); runtime jobs need one process. Resolve toolchains by trusted absolute paths and verify their versions. Python must use isolated mode and a minimal environment. Do not grant an entire developer toolchain/profile tree just to make startup work.
3. Use `STARTUPINFOEX`, `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES`, and an explicit inherited-handle list. Create suspended, assign the mandatory job, verify restrictions and resume; terminate/reap on every setup failure. See Microsoft's [process attribute API](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute). Neither a restricted token nor a normal-token retry is a fallback policy.
4. Grant no Internet/private-network capabilities and add no loopback exemption. Verify denial with an audit-created outside-workspace canary and loopback-only listener while also asserting the actual child is an AppContainer. Test file denial for compiler preprocessing, alternate include spellings, Python/native runtime reads, other job artifacts, and app-data. A refused connection without a working listener is not evidence of denial. Use a controlled isolated test environment for any later non-loopback egress check.
5. Admit one job in the desktop backend; supervise it outside the UI thread. Provide cancellation and a single outer deadline covering startup, compiler descendants, syntax checks and all cases. Drain both pipes concurrently, retain bounded data, flag overflow before comparison, and bound total retained results. Enforce memory/process/CPU limits and report MLE only from reliable supervisor evidence; an ambiguous failed allocation is Runtime Error with an explicit attribution policy, not a guessed MLE.
6. Preserve failure-injection tests for profile/token/attribute setup, creation, assignment, resume and termination errors. Require bounded cleanup after rejection, timeout, overflow and cancellation. Do not restore the legacy host runner or claim its ignored tests passed.

Open feasibility questions: g++/Python compatibility with LPAC and minimal ACL grants; enforceable quotas for **all** writable locations, including profile storage; toolchain distribution rights; startup/cleanup cost; Windows version support; and a clean-machine proof of file/network denial. A small prototype must resolve these before choosing AppContainer as the release boundary. If it cannot, a disposable offline VM with no shared folders, clipboard, credentials or network remains the stronger alternative. Neither option is a finished security boundary in this repository.

Hosting remains a separate architecture: isolated workers are necessary but do not supply tenant authorization, admission/rate quotas, retention or confidential testcase policy. There is no HTTP execution service here.
